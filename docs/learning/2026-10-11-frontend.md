# Learning session: frontend draw path

- Date: 11 October 2026
- Learner: frontend pass (agent 06), for the maintainer to reread
- Agent or task: 06 Frontend — board UI + wallet draw against the agreed contract
- Goal in one sentence: Let someone look at the wall without a wallet, and only claim a paint after a real transaction and a matching `get_pixel` read.
- Environment: mock unit tests and local Vite build; wallet connector aimed at testnet; no live mainnet journey
- Files or contract methods explored: `web/**`; `get_board`, `get_pixel`, `draw` via `FRONTEND_HANDOFF.md`

## Before starting

- What do I think should happen? Clicking a square might tempt the page to paint locally. The brief forbids that.
- What terms or steps are unfamiliar? A **view** is a free read. A **call** is a signed change. **Gas** is the network fee. **Sparse cache** means we only remember cells we have actually read.
- What is the smallest experiment that can answer one question? Can `prepareDraw` become `ready` only when a contract id is present, still without inventing a transaction hash?

## What I did

1. Kept Vite + `@hot-labs/near-connect` (already in the repo).
2. Added RPC view helpers, sparse board cache, submit flow with pending/success/failed.
3. Kept sponsorship behind a flag with ordinary-wallet fallback; left payment provider unused.
4. Documented config in `web/.env.example` and `web/README.md`.

## What I observed

- Expected result: unit tests pass; build succeeds; empty contract id still blocks send.
- Actual result: see `cd web && npm test && npm run build` after this session.
- Evidence: vitest cases for policy, mapping, tx parse, sponsorship; no testnet tx id in-repo.
- What this evidence proves: client guards and confirmation logic are wired without fake success.
- What it does not prove: a real testnet `draw` end-to-end (needs your deployed `VITE_CONTRACT_ID`).

## What I learned

- New term: **authoritative read** — a `get_pixel` (or board) result from the contract/RPC, not a guess from a click.
- One idea to explain: the wallet hash means “something was sent”; the matching pixel read means “the wall actually changed.”
- One thing to check next time: after deploy, manually walk disconnected → success once on testnet and paste the explorer link into the learning journal.

## Problems and decisions

- Decision: sparse cache instead of inventing `get_pixels`. Why: contract handoff has no full dump yet.
- Decision: page-local `SubmitDrawResult` for UI statuses so we do not overload shared error codes for “user rejected wallet.”
- Open question for the coordinator: when a full-board read method exists, replace the sparse cache warm-up.
